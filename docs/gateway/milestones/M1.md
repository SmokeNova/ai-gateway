# M1 — Server mode and the request gate

> **Status:** ✅ done 2026-11-22 (see "Result" at the end) · **Estimate was:** ~4 focused days
> Parent plan: [PLAN.md](../PLAN.md) §6.1, §8 · Evidence: [ANALYSIS.md](../ANALYSIS.md)

## Goal

After M1, the gateway process can run in **server mode**:
- It listens on two ports, a **public** one (3001, for apps behind Caddy) and an **admin** one (3002, for me over Tailscale).
- The public port answers only five endpoints, only to per-app keys, and only for lanes that key is allowed. Everything else is 404 or 401, decided **before the request body is read**.
- Everything that can leak state between end users, call out to self-update, or trust "local" requests is off or blocked.
- When server mode is off, the process behaves **exactly** like upstream, so all upstream tests stay meaningful.

M1 is the security foundation. Nothing gets deployed publicly until it's done (M2 deploys it).

## What changes compared to the plan

1. **The lane allowlist moves from M3/M4 into M1.** M0 found that upstream lets a per-app key call *any* model, including `fusion`, which fans out to many models at once. If M2 deployed M1 as originally scoped, any app key could do that. So M1 already enforces "this key may only use these lanes" and rewrites `lane:*` to upstream names. Limits (requests per minute/day) stay in M3; lane seeding and audio stay in M4.
2. **The gateway migration runner moves to M3.** M1 creates no tables, so an empty runner would be dead code for a milestone.
3. **Session isolation without editing upstream.** Reasoning memory is always on upstream and keyed by `x-session-id`, or else by the first user message. The gate gives each public request a fresh random `x-session-id`, so two end users can never share state. Cost: upstream's "sticky model per session" no longer applies across an app's requests. That's fine for a stateless API; apps send full history anyway.

## Design

### Request flow (public port)

```
request ──► gate
            ├─ role = admin if socket.localPort == GATEWAY_ADMIN_PORT, else public
            ├─ blocked on every port? (/api/update*, /api/premium*, /mcp, /v1beta, /v1/t/*, …) → 404
            ├─ public: exact method+path in allowlist? no → 404
            ├─ GET /livez → {"status":"ok"} (answered by the gate)
            ├─ Content-Length over this endpoint's limit → 413
            ├─ key: extractApiToken() → resolveAuth() → must be kind 'profile' → else 401
            ├─ app = gateway.config.json apps[profile name] → unknown app → 403
            ├─ endpoint allowed by the app's lanes? → else 403 endpoint_not_allowed
            ├─ GET /v1/models → the app's lane IDs (answered by the gate)
            ├─ neutralise headers (strip cache/idempotency/anthropic-version/request-id,
            │   Cache-Control: no-store, random x-session-id)
            ├─ JSON endpoints: parse body (express.json, same limits)
            │   ├─ body.model must be one of the app's lanes → else 403 lane_not_allowed
            │   └─ rewrite body.model: lane:fast → auto:<chain>, lane:embed-x → <family>
            └─ next() ──► upstream createApp() (host guard, helmet, CORS, its own parsers skip
                          the already-parsed body, rate limiter, requireInferenceAuth, routing…)
```

On the admin port the gate only applies the "blocked on every port" list. Everything else goes to upstream, whose own dashboard login applies.

### Why an outer app instead of editing `app.ts`

Upstream's `createApp()` returns a normal Express app, so it can be mounted inside our own: `outer.use(gate); outer.use(createApp(config))`. The gate then runs before *everything* upstream does, including its body parsers, with **zero edits to `app.ts`**, upstream's busiest wiring file. M0 checked that upstream's JSON parsers have no `verify` hooks, and that body-parser skips a body that's already parsed (stated in upstream's own comment). **Step 1 is a short spike that proves this before anything else is built**; if it fails, the fallback is a 3-line marked edit in `app.ts`.

### Files

All new code is in `server/src/gateway/`. Upstream gets one small, marked edit in `index.ts`.

| File | What it does |
|---|---|
| `gateway/env.ts` | Reads `GATEWAY_SERVER_MODE`, `GATEWAY_ADMIN_PORT`, `GATEWAY_CONFIG_PATH` |
| `gateway/config.ts` | Loads and validates `gateway.config.json` with zod (lanes, apps; limit fields accepted now, enforced in M3) |
| `gateway/startup-checks.ts` | Refuses to start on unsafe settings (list below) |
| `gateway/gate/index.ts` | The gate middleware (flow above) |
| `gateway/gate/routes.ts` | Public allowlist, everywhere-blocklist, per-endpoint body limits, exact path matching |
| `gateway/gate/auth.ts` | Key check using upstream's exported `extractApiToken` and `resolveAuth` |
| `gateway/gate/headers.ts` | Header neutralisation on requests; drops internal headers from responses |
| `gateway/gate/lanes.ts` | Lane allowlist and rewrite |
| `gateway/gate/errors.ts` | OpenAI-style error bodies: `{"error":{"message","type","code"}}` |
| `gateway/app.ts` | `createGatewayApp(config)`: outer app = gate + upstream `createApp()` |
| `gateway/server.ts` | Starts the admin listener (no ready callback, so upstream's schedulers start once) |
| `index.ts` (upstream, marked `// GATEWAY:`) | If server mode: run startup checks, use `createGatewayApp`, start the admin listener, add it to the shutdown list, raise the shutdown grace period to 50 s. If not: unchanged |
| `deploy/docker-compose.yml` | gateway publishes only `127.0.0.1:3002`; caddy publishes 80/443; data bind mount; `init: true`; `stop_grace_period: 60s`; log rotation |
| `deploy/Caddyfile` | TLS; same path allowlist; requires an `sk-cp-` key (JSON 401); per-path body limits; `flush_interval -1`; retries during restarts |
| `deploy/.env.example`, `deploy/gateway.config.example.json` | Documented examples, no secrets |

### Startup checks (server mode refuses to boot if any fail)

- `ENCRYPTION_KEY` set and not the placeholder
- `NODE_ENV=production`
- `TRUST_PROXY=1`
- `FREEAPI_BLOCK_PRIVATE_PROVIDER_URLS=true`
- `ALLOWED_HOSTS` set (both the public name and the `*.ts.net` admin name)
- `GATEWAY_ADMIN_PORT` set and different from `PORT`
- `FREEAPI_DESKTOP` unset
- context handoff off
- `TRUST_PROXY` exactly `1` (tightened after review)
- the gateway config file present and valid, and every lane referenced by an app is defined

### Tests (`server/src/__tests__/gateway/`)

Same style as upstream's tests (Vitest, a real `listen()` on ephemeral ports, `fetch`). Each test starts the outer app on **two** ephemeral ports so the port-role logic is exercised for real.

| Test | Proves |
|---|---|
| `route-inventory.test.ts` | Every route upstream mounts has a decision (public / admin / blocked). **Fails when upstream adds a route**, so the weekly sync PR forces a decision |
| `public-allowlist.test.ts` | Non-allowlisted paths 404 on the public port; `HEAD`, upper-case and trailing-slash variants 404; admin-only paths 404 publicly |
| `key-before-body.test.ts` | An anonymous 20 MB POST gets 401 without its body being read; unified key rejected publicly; profile key accepted |
| `port-role.test.ts` | Admin only on `GATEWAY_ADMIN_PORT`; any other port gets public rules; blocklist applies on both |
| `lanes.test.ts` | Unknown lane → 403; raw model IDs, `auto`, `fusion` → 403; `lane:x` rewritten to its upstream target (upstream's `routeRequest` mocked, as upstream's own tests do); `/v1/models` lists only the app's lanes |
| `isolation.test.ts` | Two requests with the same first message and the same client `x-session-id` reach upstream with different session ids; client cache and idempotency headers have no effect |
| `livez.test.ts` | Public `/livez` is `{"status":"ok"}` only; admin `/livez` is upstream's full body |
| `startup-checks.test.ts` | Each unsafe setting makes boot fail with a clear message |
| `ssrf.test.ts` | An image URL pointing at `127.0.0.1` is refused (upstream guard on) |
| `server-mode-off.test.ts` | With server mode off, `createApp` behaviour is untouched |

## Result (2026-11-22)

**Built as planned**, with no edit to `app.ts`. The outer-app spike worked on the first try. The only upstream file touched is `server/src/index.ts` (see [UPSTREAM_TOUCHPOINTS.md](../UPSTREAM_TOUCHPOINTS.md)).

| Check | Result |
|---|---|
| Gateway tests (`server/src/__tests__/gateway/`, 8 files) | **139 passed** |
| `npm run build`, `npm run lint` | clean |
| Full upstream server suite (Windows) | 5,708 passed, 9 failed. Every failure is in a file our change doesn't touch, and those 3 files pass in isolation (80/80) → load-dependent flakes. The baseline run had a *different* set of 17 flaky failures. Linux CI stays the authority |
| Real boot of the built server | Server mode refuses unsafe settings and exits 1; public port answers `/livez` and 404s `/api/ping`; admin port serves the dashboard API; normal mode is unchanged |

**Opus review findings, and what was done:**

| Finding | Action |
|---|---|
| Absolute-form request targets (`GET http://host/api/update`) slipped past the blocklist on the admin port | Fixed: anything not starting with `/` is rejected on both ports |
| A lane chain named like an upstream alias (`fast`, `smart`, `cheap`…) would route to **every** model | Fixed: reserved names rejected in the config schema; a test reads upstream's source so the list can't drift |
| `TRUST_PROXY` check accepted 2+ hops or catch-all lists (spoofable client IP) | Fixed: must be exactly `1` |
| Compressed bodies got a confusing 400 | Fixed: 415 `unsupported_encoding` before auth |
| Caddy limits were SI megabytes; STT limit had no multipart headroom | Fixed: `MiB` in Caddy, 26 MiB STT in both |
| Non-unique profile names could share one policy | Fixed: two enabled keys with the same name → 403 `app_ambiguous` |
| `X-Powered-By` could leak from upstream's host-guard responses | Fixed: stripped with the other internal headers |
| Admin listener: no separate bind address, no IPv4 fallback | Fixed: `GATEWAY_ADMIN_HOST` (optional) and the same fallback upstream uses |
| Caddyfile `{48}` regex quantifier is a Caddyfile placeholder | Fixed: `+` (the gate checks the exact key) |
| `FREELLMAPI_UPDATE_CHECK` isn't an env var upstream (it's a dashboard setting) | Removed from the checks; `/api/update` is blocked anyway |
