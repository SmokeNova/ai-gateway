## 1. Q5 Backups (`server/src/lib/db-backup.ts`)

**Answer:** There are two independent backup systems. (A) `lib/db-backup.ts` is a single-object, AES-256-GCM encrypted, gzip'd copy of the raw SQLite file, pushed to ONE target (file path, or HTTP PUT URL, or Hugging Face repo) every 5 min, with no retention and no versioning; it restores only at boot when the DB file is missing or empty. (B) `services/backups.ts` is the dashboard "Backups" page (SQL dumps into `<db-dir>/backups/`, scheduler off by default, auto-dump retention 10). WAL handling in (A) is "mostly safe, not guaranteed": a TRUNCATE checkpoint then a plain file read, not the SQLite online-backup API.

### (A) `lib/db-backup.ts`
- **Target selection (first non-empty wins):** `FREEAPI_DB_BACKUP_TARGET` (undocumented in `.env.example`, listed in `env-drift.ts:19`) > `FREEAPI_DB_BACKUP_URL` > `FREEAPI_DB_BACKUP_PATH` (`db-backup.ts:23-30`). If none is set the whole feature is a no-op (`db-backup.ts:264`). A target starting `http://` or `https://` is HTTP, anything else is a local file path (`db-backup.ts:43-45`).
- **Interval:** `FREEAPI_DB_BACKUP_INTERVAL_MS`, default 300000 (5 min); non-numeric or <=0 falls back to default (`db-backup.ts:11,36-41`). The pump runs one backup immediately at boot (`db-backup.ts:270`), then `scheduler.every(...)` (`:271`). Started from `onReady` in `index.ts:89`.
- **HTTP contract (generic URL):**
  - Upload: `PUT <url>`, headers `Content-Type: application/octet-stream` plus `Authorization: Bearer $FREEAPI_DB_BACKUP_TOKEN` only if the token is set; body = raw encrypted bytes; 30 s timeout; any non-2xx throws (`db-backup.ts:12,191-199`).
  - Restore: `GET <url>` with the same bearer header if a token is set; 404 or 204 means "no backup"; other non-2xx throws and aborts boot (`:163-173`). Aborting is good: a transient error does not lead to an empty DB being created and then uploaded over the real backup.
  - No ETag, no If-Match, no versioning, no content hash, so the receiver just overwrites one object.
- **Hugging Face special case:** if the host is exactly `huggingface.co` and the URL has the `/resolve/<rev>/<path>` shape, uploads go via `POST https://huggingface.co/api/<models|datasets|spaces>/<ns>/<repo>/commit/<rev>` as NDJSON with the blob base64'd as text; requires the token or it throws (`db-backup.ts:93-152, 181-190`). Every upload is a git commit in the HF repo (one per 5 min by default). The HF repo must be private.
- **Encryption (`db-backup.ts:55-78`):** AES-256-GCM, random 12-byte IV, 16-byte tag, no AAD. Layout: `"FAPIBK1\0"` (8 bytes magic) | IV(12) | tag(16) | ciphertext, where plaintext = `gzipSync(<entire .db file bytes>)`. Key = `FREEAPI_DB_BACKUP_KEY` if set, else `ENCRYPTION_KEY`; must be exactly 64 hex chars and not the placeholder `replace-with-64-char-hex` (`:47-53`). Note the plaintext DB already contains provider keys that are encrypted with `ENCRYPTION_KEY`, so with the default key the backup is protected by the same secret twice. A separate `FREEAPI_DB_BACKUP_KEY` is better (`.env.example:367`; `docker/README.md:83`).
- **File naming:** none. The target IS the filename (e.g. `/app/server/data/freellmapi.db.backup` in the example, `.env.example:364`). One object, overwritten each run. Local file written with mode 0600 and `restrictToOwner` (`db-backup.ts:203-212`).
- **Retention/pruning:** none for (A). Anything that needs history (rotating copies, S3 versioning, restic) has to be done outside the app, e.g. versioned storage on the receiving side, or a sidecar that copies the target file.
- **Restore (`db-backup.ts:215-242`):** runs at boot BEFORE `initDb` (`index.ts:43-48`). It only acts if the DB file is missing or 0 bytes (`:219`); if the DB file exists it is skipped, so it never overwrites live data. Procedure to restore: stop the container; remove `freeapi.db` AND any `freeapi.db-wal` / `freeapi.db-shm` (the sidecars are not restored, stale ones next to a restored file would be a hazard); set the same backup target and the same `FREEAPI_DB_BACKUP_KEY`/`ENCRYPTION_KEY`; start. The decrypted DB is written 0600. Manual/offline restore: read the file, check the magic, `aes-256-gcm` decrypt with IV/tag as above, gunzip, write out as `freeapi.db`. Restore does not bring back `.encryption-key`; in production the key comes from `ENCRYPTION_KEY` anyway.
- **WAL safety:** `backupDbNow` calls `db.pragma('wal_checkpoint(TRUNCATE)')` inside a try/catch that swallows errors (`:250-254`), then `fs.readFileSync(dbPath)` (`:256`), gzips synchronously (blocks the event loop; fine for a small DB) and uploads. The `-wal` file is never read. Gaps: (1) TRUNCATE can return busy (not throw) if a reader blocks it, in which case the main file lacks recent commits (stale, not corrupt); (2) between checkpoint and read, an auto-checkpoint (default 1000 pages) on a concurrent write could in theory yield a torn read, because it is a plain file copy, not `VACUUM INTO` or the online backup API; (3) the whole DB is read into memory. For a small single-VM DB the risk is low but not zero. Our fork can add `sqlite3 .backup` or `VACUUM INTO` from a sidecar, or a Litestream-style tool, for stronger guarantees.
- **Other:** `docker-entrypoint.sh:42-44` chowns the dir of `FREEAPI_DB_BACKUP_PATH` to `node`.

### (B) Dashboard dumps (`services/backups.ts`)
- SQL dump files `<prefix>-<stamp>-<rand>.sql` in `<db-dir>/backups` (`:131-139, :312-313`), indexed in table `backups`. Sources: manual, scheduled, pre-restore, pre-update.
- Scheduler: `startBackupScheduler` ticks every 60 s (`:634`) but the schedule is **disabled by default** (`DEFAULT_SCHEDULE.enabled=false`, `time '03:00'`, `intervalDays 1`, `:59-64`); configured via settings key `backup_schedule` (dashboard).
- Retention: `AUTO_BACKUP_DUMP_RETENTION`, default 10, 0 disables pruning; only `scheduled` and `pre-update` dumps are pruned (`:21-30, :353`).
- Excludes tables `users`, `sessions`, `url_tokens`, `migrations`, `backups`, `sqlite_*` (`:81-95`). **All other tables are dumped, including any table our fork adds**, and a restore replays the SQL. The restore compatibility check uses only upstream migration state (`schemaVersion`, `:196`, check at `:502`), so our own migration tracking table would not be validated by it.

## 2. Q6 Catalog (`server/src/services/catalog-sync.ts`)

**Answer:** The model catalog is pulled twice a day from `https://api.freellmapi.co/v1/latest`. Premium license holders get the live tier; everyone else gets a lagging monthly snapshot. The response is accepted only if an Ed25519 signature over the exact bytes verifies against a pinned public key. The catalog schema carries NO base URLs or hosts, and platforms unknown to the binary are skipped, so a catalog update cannot redirect stored provider API keys to another host. Disable with `CATALOG_SYNC_DISABLED=1`.

- **Tiers:** header comment `catalog-sync.ts:27-42`: "A valid Premium license key (Bearer) gets the live tier, refreshed every 2-3 days; everyone else gets the monthly snapshot". Request: `GET {base}/v1/latest[?since=<applied version>]`, `Authorization: Bearer <license key>` only if a license is stored (`:1090-1096`). `304` means up to date.
- **Schedule:** 10 s after boot, then every 12 h (`BOOT_DELAY_MS`, `SYNC_INTERVAL_MS`, `:58-59`; `startCatalogSync` `:1286-1300`). Also runs `refreshLicenseStatus` (`/v1/license/check`, only if a license key is stored, `:1198-1217`). No env var changes the interval.
- **Signature check:** header `x-catalog-signature` (base64) must exist; `crypto.verify(null, bytes, pubkey, sig)` (Ed25519) over the raw body bytes BEFORE JSON parsing; failure discards the response (`:1105-1109`). Pinned key in source at `:49-52` (`MCowBQYDK2VwAyEAq9yv4+3EeyMHKsfVYBhkcz1lYgIXSUeHNnN6tNgYX3k=`).
- **Version floor:** catalogs with `version < MIN_CATALOG_VERSION` (`'2026.06.07'`, `:56`) are ignored (`:1127-1133`). Verified JSON is cached in `settings.catalog_applied_json` and re-applied offline at every boot (`reapplyCachedCatalog`, `:1263-1281`).
- **Env vars:**
  - `CATALOG_SYNC_DISABLED=1` stops all polling (`:1288`). Note it also skips `reapplyCachedCatalog` (`:1292` is after the early return), so migrations' baseline is what you get. License refresh is also not run.
  - `CATALOG_BASE_URL` (default `https://api.freellmapi.co`, `:44,72`) and `CATALOG_PUBKEY` (PEM, `\n` escaped, `:113`) override the source/key. Both are undocumented in `.env.example` (listed as known-undocumented in `lib/env-drift.ts:16-17`). `PREMIUM_SITE_URL` also exists (`env-drift.ts:20`).
  - There is no "pin to version" env var. To freeze the catalog use `CATALOG_SYNC_DISABLED=1` (bundled migrations + whatever cache is in the DB).
  - Note: dashboard API also forces syncs (`syncCatalog(true)` after a license key is added; route `routes/premium` not examined).
- **Can a catalog update send stored keys to a different host? No, by construction:**
  1. Catalog types (`CatalogModel`, `CatalogEmbedding`, `CatalogTranscriptionModel`, `CatalogVideoModel`, `CatalogSearchEngine`, `CatalogDecisionModel`, `Catalog`, `catalog-sync.ts:127-271`) contain only ids, display names, ranks, limits, flags, `requestStyle`, `providerModelId`, quirks and `managedPlatforms` (names). Grep of the file for url/host/endpoint finds only the catalog service's own URL (`:44,72,1093,1184,1202`).
  2. Rows are applied only for platforms the binary has code for: chat rows require `hasProvider(platform)` and `platform !== 'custom'` (`:627-632`); media rows require `MEDIA_PLATFORMS` etc. (`:598`, `:694`, `:728`, `:783`); unknown platforms are counted in `skippedUnknownPlatform` and ignored (`:1149`). Specialist rows are limited to a hard-coded allowlist `ovh/cloudflare/xkiro` (`specialist-text.ts:10-15`).
  3. Upstream hosts are hard-coded in each provider class (`providers/*.ts`). The only DB-driven base URL is the `custom` provider: `resolveProvider('custom', baseUrl)` uses `api_keys.base_url`, set by an authenticated admin/declarative config (`providers/index.ts:717-729`; column added in `migrations/20260101_000000_legacy_baseline.ts:304-309`), guarded by `lib/url-guard.ts` (metadata/link-local always blocked, private ranges blocked with `FREEAPI_BLOCK_PRIVATE_PROVIDER_URLS=true`), and `proxyFetch` refuses redirects for custom providers (`url-guard.ts:26-29`).
- **Trust chain:** (1) the compiled-in provider hostnames and pinned Ed25519 pubkey in the image you build/pull; (2) the catalog host operator holding the private key (upstream maintainer); TLS to `api.freellmapi.co` alone is not trusted, the signature is; (3) the key-bearing `Authorization` header goes only to provider hosts in code. Residual risks: a validly signed (or malicious upstream) catalog can still (a) enable/disable models or add model ids on known platforms, steering traffic and spending quota on particular models, (b) enable "keyless" providers on a new install (`applyKeylessDefaults`, `:1123`, `keyless-defaults.ts`), (c) supply strings used in URL paths on fixed hosts (e.g. Cloudflare `.../ai/run/<model>`, `specialist-text.ts:42`), a path not host influence, (d) quirks text shown in the UI. Also, if someone can set env `CATALOG_PUBKEY`/`CATALOG_BASE_URL` they own the catalog; in our compose these come only from our `.env`. The license key (if ever set) is sent to the catalog host.
- **Phone-home:** yes, this is outbound traffic to a third party (`api.freellmapi.co`): sends only the `since` version and (if licensed) the bearer. No install id seen. Disable via `CATALOG_SYNC_DISABLED=1`. Trade-off: without it, new upstream model additions/retirements arrive only with image upgrades (the migrations are the baseline).

## 4. Migrations / DB

**Answer:** Upstream uses a hand-registered, file-per-migration runner with a table named `migrations`; it runs synchronously inside `initDb()` at every boot (except `NODE_ENV=development`). DB file default is `server/data/freeapi.db` (NOT `freellmapi.db`, despite docs), WAL on, `busy_timeout=5000`, `foreign_keys=ON`. A second runner with its own tracking table is feasible with a few caveats below. No upstream table uses a `gateway` prefix.

- **Runner:** `server/src/db/migrate/runner.ts`. Tracking table `migrations(id INTEGER PK AUTOINCREMENT, filename TEXT NOT NULL UNIQUE, applied_at TEXT DEFAULT datetime('now'))` (`:35-41`). Each migration's `up(db)` plus the tracking INSERT run in one `db.transaction` (`:163-166`). Applied-ness is by filename; ordering is the order in the registry (`:213-218`). Down = last row by id (`:173-195`).
- **Naming/registration:** files `server/src/db/migrations/YYYYMMDD_HHMMSS_name.ts` exporting `up(db)` and `down(db)` (`runner.ts:244-246`; example `20260101_000000_legacy_baseline.ts`). **Boot uses a static registry**: `DEFAULT_MIGRATIONS` in `db/migrate/defaults.ts:117+` (import per file, a filename constant, an array entry), and `runMigrationsSync` uses only that (`runner.ts:64-69`); directory scanning is for the CLI/tests (`getMigrationFilenames`, `:220-230`). Upstream PRs adding migrations therefore must touch `defaults.ts`; this also makes upstream merges conflict-prone there. `TEMPLATE.ts` + `npm run db:migration:create --name=...` scaffold it (`CONTRIBUTING.md:34-45`).
- **When:** `index.ts:43-49`: `restoreDbBackupIfNeeded` -> `initDb()` -> `connectDb` (pragmas) -> `runMigrationsSync(db,'up')` (`db/index.ts:206-208`) -> `initEncryptionKey` -> `probeStoredSecrets` -> then `applyDeclarativeConfigFromEnv`, listener, schedulers. In `NODE_ENV=development` migrations are NOT auto-run (exits with a hint, `db/index.ts:209-220`). Docker sets `NODE_ENV=production`, so they run at boot. A migration failure rejects `main()` and exits 1 (`index.ts:149-156`).
- **DB path:** `FREEAPI_DB_PATH` (trimmed) else `path.resolve(<server/dist/db>/../../data/freeapi.db)` = `/app/server/data/freeapi.db` in the image (`db/index.ts:15,27-29`; `lib/config.ts:85`). `docker/README.md:79` and `.env.example:350` claim `freellmapi.db`, which is only an example name; with no env var set the actual file is `freeapi.db`. Encryption key file (non-production only) is `.encryption-key` in the same dir (`lib/crypto.ts:27,63-68`).
- **Pragmas** (`db/index.ts:82-87`): `journal_mode = WAL` (unless `:memory:`), `foreign_keys = ON`, `busy_timeout = 5000`. `synchronous` not set (SQLite default). Android uses node:sqlite factory (`:45-47`). The data dir is chmod'ed to the owner when it is the default data dir or created by the app; `FREEAPI_DB_DIR_HARDENING=0|1` overrides (`:122-147`). Beware: pointing `FREEAPI_DB_PATH` at a pre-existing mounted dir leaves permissions as they are.
- **Constraints for our second runner (own tracking table):**
  - Use `getDb()` (same single better-sqlite3 connection) and run it AFTER `initDb()` returns (upstream first creates/uses `migrations`); never touch table `migrations`.
  - Table names to avoid (all upstream, from `migrations/*.ts`): `models, api_keys, requests, rate_limit_usage, rate_limit_cooldowns, fallback_config, profiles, profile_models, settings, users, sessions, provider_quota_state, provider_quota_observations, embedding_models, media_models, quirks, quirk_targets, catalog_model_tombstones, model_overrides, request_hourly, request_attempts, url_tokens, client_profiles, custom_model_tombstones, playground_conversations, server_logs, backups, idempotency_claims, response_cache, key_monthly_usage, model_probe_status, search_requests, decision_requests, cloudflare_neuron_usage, model_monthly_usage` and the transient `models_endpoint_identity`, `media_models_rebuilt` (created by rebuild migrations). Prefix `gateway_` is unused (grep for `gateway_` in `server/src`, excluding tests, = 0 hits; no `CREATE TABLE ... gateway*`). Still, a stricter distinct prefix such as `fork_`/`aig_` reduces any chance of future upstream collisions.
  - `foreign_keys=ON` is global; upstream rebuild-style migrations run `PRAGMA foreign_keys=OFF` around table rebuilds (see `migrations/20260729_000001...`), so do not add FKs from our tables into upstream tables that upstream may rebuild (`models`, `media_models`, `api_keys`) unless you accept that.
  - `db:migration:fresh` (`migrate/cli.ts:186-206`) drops ALL non-sqlite tables, including ours (dev only, never in prod).
  - Dashboard SQL dumps/restores include our tables (see Q5-B) and validate only upstream schema version.
  - Upstream test suites that open an in-memory DB via `initDb` will not know our tables, which is fine as long as our runner is invoked from our own code path/entrypoint.
  - Upstream does not hold a long write lock after boot, but request logging and health writes happen concurrently; with `busy_timeout=5000`, keep our migrations short.

## 5. Docker

**Answer:** Multi-stage Node 24 slim build; final image has no `USER` (runs as root only for `docker-entrypoint.sh`, which chowns the data dir then `setpriv`-drops to `node`); one named volume at `/app/server/data`; port 3001 bound to 127.0.0.1 by default; healthcheck on `/api/ping`; Watchtower is present but opt-in behind a compose profile and not started by default. Compose's `image:` points at upstream's GHCR image, which must be changed for the fork.

- **`Dockerfile` (`:1-86`):** `ARG NODE_IMAGE=node:24.22.1-bookworm-slim`, stages deps (adds python3 make g++ for better-sqlite3, `npm ci`), build (`npm run build`, `npm prune --omit=dev`), runtime. Runtime: `ENV NODE_ENV=production PORT=3001 FREELLMAPI_INSTALL_METHOD=docker`, copies node_modules/shared/server dist/client dist/`desktop/package.json` (version only) with `--chown=node:node` (`:35-53`); `mkdir -p /app/server/data && chown node` (`:55`); entrypoint copied 0755 (`:60`); build-arg `FREELLMAPI_COMMIT_SHA` as env (`:64-65`); `USER root` (`:69`) with entrypoint; `EXPOSE 3001`; no `VOLUME` on purpose (`:75-81`); `CMD ["node","server/dist/index.js"]`. The `node` user is the official image's (uid/gid 1000, an assumption of the base image, not stated in the repo; the entrypoint resolves it dynamically with `id -u node`, `docker-entrypoint.sh:33-34`).
- **`HEALTHCHECK`** (`Dockerfile:83-84`): every 30 s, timeout 5 s, start-period 15 s, 3 retries; node fetch of `http://127.0.0.1:${PORT:-3001}/api/ping`. Compose repeats the same on fixed port 3001 (`docker-compose.yml:35-46`). Note `ALLOWED_HOSTS` middleware: the 127.0.0.1 Host header is loopback, which is always accepted.

## Key risks/flags for our fork (summary)
1. **Compose pulls `ghcr.io/tashfeenahmed/freellmapi:latest`** and ships Watchtower profile; change image, drop Watchtower, never mount docker.sock.
2. **Catalog phones home** to `api.freellmapi.co` (twice daily); cannot redirect provider keys (no URL fields, hosts hard-coded), but can change model sets; `CATALOG_SYNC_DISABLED=1` stops it (and also the offline re-apply).
3. **Behind Caddy, set `TRUST_PROXY=1`** or all clients share one IP for rate limiting; set `ALLOWED_HOSTS`, `HOST_BIND=127.0.0.1`, `FREEAPI_BLOCK_PRIVATE_PROVIDER_URLS=true`, `FREELLMAPI_UPDATE_CHECK=off`.
4. **Health checker has no off switch** and probes every key every ~5 min (+ full burst on VM wake); metered probes exist for few providers. `COOLDOWN_PROBE_DISABLED=1`; leave `MODEL_PROBE_ENABLED` unset.
5. **DB backup:** single overwritten object, no retention, 5 min cadence, plain file copy after WAL checkpoint (not a true online backup), key defaults to `ENCRYPTION_KEY` (set a separate `FREEAPI_DB_BACKUP_KEY`). Restore only when DB file is absent.
6. **DB filename is `freeapi.db`** (docs say `freellmapi.db`); upstream migrations are statically registered in `defaults.ts`; our tables are included in dashboard dumps; avoid names in the upstream table list above.
7. **Workflows:** disable/delete `cli-release.yml` and `desktop-release.yml`; `v*` tags trigger both docker and desktop builds; docker.yml pushes to GHCR under our owner; arm64 runner may be unavailable on a private repo; do not enable Pages for `docs/`.
8. `RESPONSE_CACHE_PERSIST` defaults to true (plaintext answers in SQLite) if the cache is switched on; `REQUEST_ANALYTICS_LOG_CLIENT=true` stores client IP and UA.
